# 数据清洗与构建方案

> 目标：把天池下载的原始两份 CSV 变成**可复现、可核算、无泄漏**的训练/验证/测试 Parquet，并让论文表 1、图 2 的所有数字都能由 `src/data/stats.py` 一键重算。
> 对应阶段：W3–W6（见 `03-里程碑与验收.md`）；对应代码：`src/data/prepare_aliccp.py` 的四个 `TODO(真实数据)`。

## 1. 产出物与验收口径

| 产出           | 路径                                             | 验收标准                                    |
| ------------ | ---------------------------------------------- | --------------------------------------- |
| 原始清单         | `data/aliccp/00_raw/manifest.json`             | 每文件字节数 + md5 + 行数，重跑能比对                 |
| 中间字典         | `data/aliccp/10_interim/common_index/`         | 可删可重建，不参与最终交付                           |

**唯一硬门槛**（按本机实际文件，非全量 Ali-CCP）：train 曝光 **42,300,135**、点击 **1,644,256**、转化 **9,032**；test 曝光 **43,016,840**、点击 **1,673,447**、转化 **9,421**。偏差 > 0.5% 就不许进基线复现，先查是不是文件截断或解析错位。

## 2. 原始数据形态（先探测，再写代码）

Ali-CCP 是两张表，按 `user_id` 关联（**不是** `common_feature_index`——本数据集的两张表都只有 `user_id`）：

| 表                                  | 关键列                                       | 用途                                       |
| ---------------------------------- | ----------------------------------------- | ---------------------------------------- |
| `sample_skeleton_{train,test}.csv` | `行号, click, conversion, user_id, 整数, 特征串` | 每行的曝光骨架 + 两个标签（**click 在第 1 列，不是第 0 列**） |
| `common_features_{train,test}.csv` | `user_id, feature_count, 特征串`             | 用户/商品/上下文的稀疏特征                           |

> 已按实测数据修正，逐字节依据见 [08-数据探测记录.md](08-数据探测记录.md)。

**第一步永远是打印字节，不是照抄博客**。拿到文件后先做三个探测：

```python
# 1) 看前 5 行的原始字节，确认三种分隔符：列间、特征间、ID与取值间
for i, line in enumerate(open(p, "rb")):
    print(repr(line))
    if i >= 4: break

# 2) 看字段数是否稳定：按列分隔符切分，统计每行段数，出现 ≠ 期望值的行数
# 3) 看标签取值域：click / conversion 是否只有 {0,1}，有没有空值
```

探测结果写进 `doc/202610-选题/08-数据探测记录.md`（只记事实，不记猜测），**这是后续所有解析参数的唯一来源**。控制字符常见形态是 `\x01` / `\x02` / `\x03`，但必须实测。

## 4. 九步流水线

每步写清「输入 → 输出 → 校验 → 卡住时怎么办」，不做隐性降级。

| 步骤      | 做什么                                                                             | 校验                                 | 卡住时                                   |
| ------- | ------------------------------------------------------------------------------- | ---------------------------------- | ------------------------------------- |
| S0 校验   | 记字节数、md5、行数到 `MANIFEST.md`                                                      | 与下载器 `manifest.json` 的字节/md5 一致    | 不一致就重下，不要用残缺文件                        |
| S1 解析骨架 | 按实测分隔符切列，解析时间戳，标签转 `float32`                                                    | 每行段数恒定；标签 ∈ {0,1}；时间戳可解析比例 > 99.9% | 段数漂移说明分隔符猜错，回 S0 重探                   |
| S2 建字典  | `common_features` 按 `common_feature_index` 哈希分 64 桶写 Parquet                    | 桶内 index 唯一；总条数与原始行数一致             | 内存不够就加桶数，不要两表全载                       |
| S3 join | 流式扫骨架表，按 index 查字典拼特征串                                                          | join 命中率 > 99.9%，未命中计数写入 stats     | 命中率低说明两表版本不匹配，停                       |
| S4 选域编码 | 23 个稀疏域 → `int32` 矩阵；缺失填 0，OOV 填 1                                              | 每域取值 `< field_dim`；无负数             | 域 id 与预期不符时以实际文件为准并更新 `SPARSE_FIELDS` |
| S5 词表   | **只用 train** 统计频次，频次 < 5 归 OOV                                                  | test/val 里的新值 100% 落到 OOV          | 若 OOV 率 > 5%，说明词表过小或缺域                |
| S6 划分   | test 原样不动；train 随机 5% 作 val（固定种子 0）                                             | 三段 `user_id` 可分；val 转化数 ≥ 800      | val 转化太少就提到 8%，并写进论文实验设置              |
| S7 落盘   | Parquet + snappy，200 万行/片；列：`ids`(23×int32)、`click`、`conversion`、`user_id`(哈希后) | 回读行数与 S1 一致；单文件 < 200 MB           | 分片过小会产生小文件，按 S7 阈值合并                  |
| S8 画像   | `stats.py` 输出 `stats.json`                                                      | 见第 6 节断言表                          | 任一断言失败就停下修数据                          |

> 与 `02-研究方案摘要.md` 的「七步」对照：S0–S1 对应第 1–2 步，S2–S3 是「流式解析 + join」拆成的读/写两半，S4–S5 是第 3–4 步，S6–S7 是第 5–6 步，S8 是第 7 步。口径一致，这里只是把每步的校验与失败动作补齐。

## 5. 清洗规则（逐条可计数）

清洗**不做静默修正**：每条规则都要计数并写进 `stats.json` 的 `cleaning` 段，论文附录直接引用这些数字。

| 编号  | 规则      | 判定                                             | 处理                   | 理由                              |
| --- | ------- | ---------------------------------------------- | -------------------- | ------------------------------- |
| C1  | 重复曝光    | 全字段完全相同（含 `user_id`+`adgroup_id`+`time_stamp`） | 去重，保留首条              | 重复行会放大权重、扭曲 CTR                 |
| C2  | 逻辑矛盾    | `conversion=1` 且 `click=0`                     | **整行丢弃**并计数          | 没点击不可能转化，属采集错误；改成 click=1 会造假标签 |
| C3  | 标签缺失    | `click` 或 `conversion` 为空/非 0-1                | 丢弃                   | 无法监督                            |
| C4  | 骨架无公共特征 | S3 join 未命中                                    | 丢弃并计数；命中率写入 stats    | 23 域全缺失的样本等价于噪声                 |
| C5  | 特征域缺失过多 | 单条样本缺失域数 > 12（> 半数）                            | 保留，但在 stats 里单列缺失率   | 直接删会引入新的选择偏差，不删更安全              |
| C6  | 时间戳异常   | 无法解析，或落在数据集声明区间之外                              | 丢弃并计数                | 时间穿越会造成泄漏                       |
| C7  | 词表外新值   | val/test 出现 train 未见取值                         | 映射为 OOV(1)，**不丢弃**   | 线上本来就会遇到新值，丢弃会高估效果              |
| C8  | 极端重复用户  | 单 `user_id` 曝光占比 > 0.5%                        | 保留，但统计里报 top-10 用户占比 | 删除会破坏分布；先看是否爬虫/机器人              |

> **C2 的外部一致性**：ESMM 系实现同样把「CTR=0、CVR=1」定义为不合法样本并删除（见 `11-文献笔记.md` 第 1 则）。本条不依赖该说法成立——实测 train 230 条、test 226 条，仅凭「没点击不可能转化」已足以判定为采集错误。

> S4 的缺失编码与 C7 的 OOV 编码必须是两个不同 id（0 与 1），否则「缺失」和「没见过」会被模型混为一谈——这是复现 Ali-CCP 最常见的隐性错误之一。

## 6. 质检断言表（写成脚本，失败即中断）

```python
assert 0.9 <= exposure / 84_000_000 <= 1.1
assert 0.9 <= click / 3_400_000 <= 1.1
assert 0.9 <= conversion / 18_000 <= 1.1
assert 0.03 <= ctr <= 0.05                       # 官方约 4.0%
assert 0.003 <= cvr_click_space <= 0.008         # 0.53% 附近
assert abs(ctcvr - ctr * cvr_click_space) < 1e-4 # 乘法分解自检
assert oov_rate_val < 0.01 and oov_rate_test < 0.02
assert val_conversion >= 800                     # 够算置信区间
assert ids.max(axis=0) < field_dims              # 无越界（否则 embedding 直接崩）
```

最后一条最容易在训练时才炸，务必在落盘前断言。

## 7. 数据泄漏防线（四条红线）

1. **词表只用 train 统计**；val/test 的取值一律查表，查不到进 OOV。反例：用全量数据建词表，会让 test 的稀有值获得独立 embedding，AUC 虚高。
2. **温度 T、α、早停轮数、损失权重只在 val 上调**；test 只在最终报告时打开一次。
3. **C1 去重只在 train 内执行**：test 不做 C1 去重，保持原始分布；C2 属采集错误（无点击不可能转化），三段都删并计数（实测 test 226 条，见 12 号记录 E13）。test 不参与词表统计，也不做任何统计性改写。
4. **`user_id` 只用于 GAUC 分组，绝不进特征**；落盘前做哈希脱敏（`md5(user_id + salt)` 取前 16 位），既合规又保留分组能力。

## 8. 10% 采样集怎么造

全量跑一轮要几小时，调参期用 10% 采样集：

- **分层抽样**：按 (click, conversion) 四个格子分别抽 10%，保证三级转化率不变；
- 固定种子 0，采样脚本与全量解析共用同一份代码（只多一个 `--sample 0.1`）；
- 采样集只用于调参与冒烟，**论文数字一律来自全量**，并在实验设置里写明这一点；
- 验收：采样集的 CTR/CVR/CTCVR 与全量偏差 < 10%，否则说明分层写错。

## 9. 与 Hive / Spark 的对应

本地脚本能跑通后，把同一套规则搬到集群（论文第 6 章的内容）：

| 层   | 表                                           | 内容                               |
| --- | ------------------------------------------- | -------------------------------- |
| ODS | `ods_aliccp_skeleton` / `ods_aliccp_common` | 原始 CSV 落表，只做类型转换                 |
| DWD | `dwd_aliccp_exposure` / `dwd_aliccp_user_feature` | 曝光明细（10 个骨架域）+ 用户维表（12 个公共域）；join 推迟到 ADS，避免用户特征 58 倍冗余 |
| DWS | `dws_aliccp_vocab` / `dws_aliccp_user_stat` | 域取值频次与编码索引；用户级曝光/点击/转化聚合        |
| ADS | `ads_aliccp_train` / `ads_aliccp_profile`   | 编码样本（22 域 × K=8）+ 论文表 1 画像指标     |

要点：存储格式与「DWD 为何拆两张表」见 `02-研究方案摘要.md` §5.1（ODS/DWD 用 ORC + Snappy，ADS 用 Parquet）；解析特征串用 Spark 原生 `split` / `explode`（避免 Python UDF）；DWD 保留全量曝光（85,316,975 行），C2 在 ADS 前删除，使 DWD 对 `_encoded`、ADS 对 `20_processed` 各有一个对账锚点；DWD 落表后 `ANALYZE TABLE` 收集统计信息。

## 10. 代码落地顺序

`prepare_aliccp.py` 里四个 `TODO` 按依赖顺序实现，每个都能单独验收：

1. `build_common_index` → 用 `interim/common_index` 的行数验证（应等于 common 表行数）；
2. `stream_join` → 用 train 前 1 万行的 join 命中率验证；
3. `build_vocab` → 用「test 新值全部落 OOV」验证；
4. 编码落盘 + 分片 → 用回读行数与 `ids.max()` 断言验证。

`dataset.py` 的读取约定：特征列 = 除 `label_cols` 与 `user_id` 外的所有列，顺序必须与 `field_dims` 严格一致——**列顺序错位不会报错，只会让 AUC 悄悄掉 0.1**，所以落盘时把列名写进 `schema.json`，读取时校验。

## 12. 风险与降级

沿用 `04-风险登记.md`：R1（下载/解析受阻）→ 先用 10% 采样集跑通全链路；R2（复现对不上）→ 优先怀疑数据而非模型，按第 6 节断言逐项排查。本方案新增一条：**C2 逻辑矛盾行的比例如果超过 0.5%，说明骨架表与特征表版本不匹配**，此时不要清洗，先回 S0 重下。
