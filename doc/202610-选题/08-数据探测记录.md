## 2. 列结构（实测）

### 骨架表 `sample_skeleton_*.csv` —— 6 列

```
0: 行号(1,2,3,...)   1: click   2: conversion   3: common_feature_index   4: 整数(9/10/14/21…)   5: 特征串
```

**关键：第 0 列是行号，标签在第 1、2 列**——这是本项目最容易踩的坑。若误把第 0 列当 click，
CTR 会算成 1.4e-7（已实际踩过，见本节末「踩坑记录」）。

- 第 1 列 `click ∈ {0,1}`，第 2 列 `conversion ∈ {0,1}`
- 第 3 列官方名 **`common_feature_index`（公共特征组索引）**，是 16 位 hex 串，**不是用户 ID**。
  它只用于 join 与 GAUC 分组，不作特征。实测 train 730,600 个不同索引、test 884,212 个；
  42,300,135 ÷ 730,600 ≈ 57.9 条曝光/组，即一个索引约对应一次请求页。组/用户（按域 101 计）
  = train 2.48、test 2.99
- 第 4 列是整数（观测到 8–21），无标签信息，建议丢弃
- 第 5 列是稀疏特征串，格式见第 3 节

实测样例（`<01>` 等为控制字符占位）：

```
1,0,0,bacff91692951881,9,210<02>9052218<03>1.0<01>210<02>9064553<03>1.0<01>...
3,1,0,bacff91692951881,20,210<02>9089731<03>1.0<01>509<02>9511769<03>2.30259<01>...
```

### 公共特征表 `common_features_*.csv` —— 3 列

```
0: common_feature_index   1: feature_count   2: 特征串
```

`feature_count` 与实际切分出的特征个数**一致**（已抽查 343 与 1025 两行，逐一对上），可直接用作解析自检。

### 域 101 = 用户 ID（2026-11-10 实测）

| split | 唯一 101 值 | 每组出现次数 | join 后每值曝光次数 |
| --- | --- | --- | --- |
| train | **294,882** | 1–4（mean 2.47，max 4） | 1–3,532（mean 143.1，p50 84，p90 354） |
| test | **295,787** | 1–8（mean 2.98，max 8） | 1–3,500（mean 145.1，p50 86，p90 357） |

- 唯一值约 **29.5 万**，与官方「约 40 万用户」同阶；若是商品（110_14）会是千万级，若是会话会是 4,200 万级，因此 **101 是用户 ID**。
- 每个特征组都带一个 101，即一组 ≈ 该用户的一次请求页；train 组数 730,600 ÷ 294,882 ≈ 2.5 组/用户。
- **统计陷阱**：在 L1 去重表上计数，101 每值只有 1–4 次（< `MIN_COUNT=5`）→ 全量 OOV；但 join 到曝光后 **train 89.18% / test 89.11%** 的取值 ≥5 次。词表必须在**曝光级**统计，见 12-E33b。

## 3. 特征串分隔符（与常见博客写法不同）

| 字节 | 名称 | 作用 |
| --- | --- | --- |
| `0x01` | SOH | **特征之间的分隔** |
| `0x02` | STX | **field_id 与 feature_value 之间** |
| `0x03` | ETX | **feature_value 与 weight 之间** |

单个特征：

```
field_id <02> feature_value <03> weight
```

解析代码：

```python
for item in feature_string.split("\x01"):
    field_id, rest = item.split("\x02", 1)
    value, weight = rest.split("\x03", 1)
```

实测自洽性：train 首行 `0x01` 出现 8 次 → 9 个特征，`0x02`/`0x03` 各 9 次；
公共特征表首行 `feature_count=343`、`0x01` 出现 342 次 → 343 个特征，完全对上。

两点必须记住：

- **`weight` 不是 1.0**：如 `0.69315`（= ln 2，表示该取值计数为 2）、`3.28343`。这是 Ali-CCP 的计数取对数权重，建模时默认丢弃，但要在论文数据章节说明。
- **`field_id` 可能是复合串**：如 `150_14`，不能 `int()` 强转，必须先当字符串再映射词表 id。

## 4. 标签分布（实测，可直接用于论文表 1 的对照）

| 指标 | train | test |
| --- | --- | --- |
| 曝光 | 42,300,135 | 43,016,840 |
| 点击 | 1,644,256 | 1,673,447 |
| CTR | 3.8871% | 3.8902% |
| 转化（点击空间） | 9,032 | 9,421 |
| CVR | 0.5493% | 0.5630% |
| CTCVR | 0.02135% | 0.02190% |

三点结论：

1. **CTR 3.89%、CVR 0.55% 与 Ali-CCP 公开口径吻合**，说明解压正确、列对齐正确。
2. train/test 的 CTR 与 CVR 几乎相同，说明两边的 logging policy 一致，**test 可直接当独立验证集**，不需要额外重加权（但第五章仍要报告曝光空间与点击空间的 AUC 差异，这才是本课题的核心现象）。
3. **`click=0` 但 `conversion=1` 的行：train 230 条、test 226 条**，占比转化样本的 2.5% 左右。这正好印证 06 文档的清洗规则 C2——该行是采集错误，必须丢弃（不能把 click 改成 1 伪造）。清洗后 train 转化数应为 **8,802**。

## 7. 踩坑记录

第一次统计 CTR 得到 `1.4e-7`，原因有三，都记下来避免重犯：

1. **列错位**：把第 0 列（行号）当成了 click。行号只有一行是 `1,`，所以「点击」只剩 6 条。
2. **按字节块切行丢了半行**：`read(4MB).split(b"\n")` 后直接丢掉末段，会漏掉每块的最后一行，必须先 `carry` 到下一块。
3. **切分次数要用 `split(",", 5)`**：只切前 5 个逗号，第 5 列特征串不回切，避免误伤。

另有一次差点漏掉的问题：集中精力看分隔符时，先入为主按博客的 `click` 在第 0 列写代码，而实际样本多了前置的行号列。**换成新数据源时，先跑一遍「逐列取值分布」比读博客可靠。**
